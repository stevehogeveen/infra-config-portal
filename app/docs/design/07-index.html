Six Lab Builder directions for usability sessions

These six mockups are candidates for usability sessions. Three are drawn for complete non-IT participants who have never configured a server, and three for professional participants who run labs for a living. All six keep the same functionality: the rack and its kit actions, adding and editing equipment, connecting with the verified disk erase, network settings, checking firmware, first-contact failures, the guarded write steps, and the locked ESXi and Windows steps.

Nothing here is decided. Each direction was judged twice, on the same seven dimensions out of 10. The judges scored the version before each direction's last revision pass, so a verdict can name a problem the file has since fixed. What the designer left open after that pass is listed at the foot of each card.

Designer's summary

Lab Builder drawn as the companion app for a home appliance, for a complete non-IT user on a laptop or tablet. Warm cream surfaces, rounded 22-28px cards with soft shadows, 17px body and 44px Fraunces headlines, one cobalt primary button per screen whose label is a verb sentence ("Carry on with the server's drives", "Save this layout and continue", "Plan the new RAID", "Try the connection again", "Compare the server with the package"), a six-dot progress row reading "2 of 6 done" with the two locked steps carrying their reasons, and a plain-English line under every technical noun plus small "What does this mean?" expanders. Provenance is a chip on every value: green "checked 08:35" only for proven readings, sand "from your plan" for saved values, dashed "not known yet" for blanks; the never-answered server in the failure screen shows no model or bay count. The rack is a CSS cabinet with shelf numbers, LED dots and drive-bay/port faces; Add equipment keeps the full customization (4-60 U stepper, seven-card palette with CSS thumbnails, cobalt drop preview naming shelves 5 and 6 with "Nothing else moves", red take-out zone, edit card with 10-bay tap grid, save layout/copy/load). Connect equipment shows the six-disk verified erase with its three timestamps, the two-drive boot-pair note, the 10-alert notice, and four side actions that open a shared guarded dialog (exact command, then a separate typed confirmation for writes). Blocked items (PDUs with no sign-in, the switch firmware, Review upgrades, Continue to Prepare ESXi) stay visible and disabled with their reason beside them. A designer's note maps every required control to its screen. Dark theme redefines the tokens as warm charcoal with cobalt lifted to a lighter tint.

Left open by the designer after revision (6)
  • VM storage ('Where virtual machines are stored') stays on the Network settings screen and is not moved into the RAID plan. The brief's functionality list places VM storage under Network settings, so moving it risks a 'missing from Network' finding. It now has a datastore plain line and the disabled NetApp option with its reason.
  • Network is not split into separate sub-step screens with their own verb buttons. It is two clearly headed sections, basics and optional extras, on one screen with one primary. Splitting further would add screens and buttons beyond the one-primary pattern.
  • My Rack still shows facts, readiness and the six steps below the fold instead of in a tap-to-open device sheet. The primary is now in the first view and the rack is sticky, which covers the next-step concern while keeping every reading visible at rest, as the page contract requires.
  • Fraunces is kept as the display face. The reviewer suggested a less default face, but Fraunces is part of this direction's identity. Distinctiveness was raised instead with manual-page folios and by reserving cobalt for the primary. Per-screen CSS device illustration headers were not added.
  • The bay mapping uses HPE's port:box:bay reading of the controller IDs (2I:1:5 = bay 5). The mismatch this produces against the brief's planned bays (1-4, 6-9) is shown honestly as amber plan-vs-server rows rather than hidden or reconciled by changing the given facts.
  • Hover tooltips (title attributes) on Build reports and Run history are the only explanation for those two pills. The kit menu explains 'kit' and the pill text says '8 shelves (8U)'.

Designer's summary

An illustrated instruction-manual take on Lab Builder for a complete non-IT audience: manila-paper surfaces, 4px ink outlines with hard offset shadows, one flat colour per equipment kind (server blue, switch yellow, PDU coral, storage teal, power violet), pictograms built from CSS (bays, ports, outlets, batteries, drives, padlocks), numbered circles for sequence, and tilted green stickers that appear only for proven values and always carry their timestamp. The rack is drawn as a physical object with feet and numbered slot callouts you tap; Add equipment opens with a "You have: 1 server, 1 switch, 2 PDUs, 0 storage" parts sheet, a seven-card parts palette, a picked-up DL380 with a dashed drop preview over slots 5 + 6 ("nothing moves"), a red bin remove zone, the -/+ 4-to-60 U height control and an Edit card with a ten-square bay grid. Connect equipment shows the sign-in form, the proven answer, and the Drives & RAID verified erase as a sticker with three stage stickers and six disk pictograms; Network, Check firmware (Continue dashed with "Compare the server first") and an "If it fails" screen (Sign-in refused, with all seven failure kinds as pictures and a fully blank device card) complete the set. Prepare ESXi and Install Windows are padlocked steps with their reasons. A yellow "1 see the command, 2 say yes, 3 it runs" strip states the write guard once per screen. Six tabs (role="tab", aria-selected) toggle hidden sections; a page-level Dark/Light toggle exercises the second theme; the designer's note maps every required control to its screen. Only touched this one file.

Left open by the designer after revision (11)
  • No <!doctype html> and no <html lang>. The page contract forbids doctype, html, head and body tags. I added the charset and viewport meta tags, but opened raw from disk the page still renders in quirks mode. The artifact host is expected to supply the doctype.
  • Kept the step order the brief gives rather than the reviewer's 'next = 4 Check firmware'. The facts say step 3 is current, and rule §7 requires diagnosing alerts before approving firmware. So the banner, the strip and the primary button all point to step 3 'look at the 10 alerts', and they agree with each other.
  • The drive facts in the brief contradict each other: occupied bays 1–4 and 6–9 against an erase record with a disk at 2I:1:5. I did not rewrite the facts. I show them as two provenances (your drawing = saved plan, erase record = recorded 24/09 16:22) with a warning naming the differing bays and 'Read drives now'. The 08:35 check no longer claims to have read the drives.
  • The recorded 24/09 erase is drawn in an ink double-ruled 'recorded' style rather than the outlined green one reviewer suggested. Rule §3 reserves green for current proof, so any green on a result from the previous day felt risky.
  • Did not draw specific alert pictograms such as 'disk 3 · warning'. The facts contain only the count (10, recorded before the erase), so naming alert types would invent hardware facts. The strip says what each one is about shows up when you look.
  • Only 'Sign-in refused' is drawn as a full failure screen. The other six kinds are a flat picture key, not clickable cards.
  • At rest, Add equipment shows the Placing card (the drop preview is the showpiece), so the DL360 3 Edit card with the per-bay grid, Move and Remove is one tap away: tap any rack piece or 'Put it back'. It is not visible at rest. The new DL380's bay grid stays empty until the operator types a bay count, because the rules forbid guessing one.
  • Kit actions (choose, rename, save as new, reports, history) now sit in a closed menu one tap away, not visible at rest, as the reviewer asked.
  • The 08:12 network save time and the 08:41 failure time come from the previous revision and the hypothetical failure scenario. They are not in the fact list, and I kept them for continuity.
  • Dark mode was fixed at the token level (shadows, contrast, swatch labels) but not screenshot-checked in this pass. Only light renders were reviewed, per the one-render-pass limit.
  • The monospace for identifiers relies on system fonts (Cascadia Mono, Consolas, ui-monospace), because the contract allows only Google Fonts via one link and I did not add a third family.

Designer's summary

Lab Builder as a guided conversation for a complete non-IT person on a tablet. A 1360px frame splits 30/70: the left column is a narrator that speaks in short serif sentences, keeps every past sentence as a threaded trail, and offers exactly one Clay button per state; the right side shows the thing being talked about in quiet warm-paper chrome that never blinks. Six screens (My Rack, Add equipment, Connect equipment with the verified erase result, Network settings, Check firmware, and a designed "No inventory permission" first-contact failure) sit behind role=tab buttons over hidden sections, with a light/dark toggle. The signature detail is the narrator explaining each provenance chip in words the first time it appears ("Green means the server itself told us this, at 08:35 today. Only that is ever green."), with green reserved strictly for proven values with a timestamp and a dotted "not known yet" chip for anything the hardware has not said. The rack is a soft illustrated elevation with a live drop preview naming U5-U6 and "Nothing else moves", a hardware shelf, a take-out zone, a rack-height stepper (4 to 60), and an edit panel with a per-bay grid. Blocked buttons stay visible with their reason beside them, and the Designer's note includes the palette, the type pairing, a drawn two-pane guarded-dialog shape (exact command, then a separate yes) and a table mapping every required control to its screen. Renders at 1440 with no console errors and no horizontal page scroll at 400px.

Left open by the designer after revision (6)
  • No <!doctype html>, so the page still renders in quirks mode. The page contract forbids doctype, html, head and body tags. I added a viewport meta tag and set explicit table font inheritance to limit quirks effects, and the artifact host is expected to supply the doctype.
  • No <meta charset>. The contract requires the file to start with <title> then <style>, so a charset meta could not go in the first 1024 bytes. Non-ASCII glyphs rendered correctly in every check.
  • The wording and severity of the 10 alerts are illustrative. The fact set gives only the count and that they were recorded before the erase, so I kept the entries close to known facts (bays 5 and 10 empty, 2 unidentified drives, time service off, self-signed certificate) and marked every one 'not checked yet'. The product owner should replace them with real recorded wording.
  • The exact erase request uses HPE's SmartStorageConfig PhysicalDriveErase shape with ErasePattern 'SanitizeRestrictedOverwrite'. It is not in the fact set, and the exact pattern string should be checked against the backend provider before it is treated as literal.
  • The mapping from front bay to controller location (for example 2I:1:5 to a physical bay) is shown as 'not matched yet' rather than invented. So the bay grid and the drive list are still not linked visually.
  • 'Open the iLO page' and 'Get HPE SPP link' are drawn as buttons with no real targets, because the mockup must not contain external links or hostnames.

Direction 04 "Instrument" renders Lab Builder as a Rams/Braun/Teenage Engineering bench console for professional operators: bone off-white surfaces, graphite type, hairline rules on an 8 px grid, embossed keys, a knurled rack-height stepper, physical toggles, and a signature LCD readout strip across the top with ghost-segment displays for Kit, Step (3·6 CONNECT), Last proof (08:35 TODAY) and Blockers (02 FIRMWARE · ALERTS). The rack is an SVG front elevation with U ticks, rail holes, a dimension line (8 U / 355.6 mm), per-bay occupancy for the DL360, 24+4 SFP ports for the Catalyst 9300, and outlets for both PDUs; the Add equipment screen reuses it with a dashed signal-red drop preview (HPE DL380 into U5–U6, nothing moves) plus a remove-from-rack zone, seven-card palette, and a full edit panel with a 10-bay grid. One signal red marks primary keys, the current step and every blocked reason; green is used only for proven values with timestamps; saved/suggested/blank chips carry every other value. Six screens (My Rack, Add equipment, Network settings, Connect equipment with the verified 6-of-6 erase result and a guarded Erase-disks-again dialog specimen, Check firmware with blocked Continue and its reason, and a Certificate-not-trusted first-contact failure with all seven named failures) switch via role=tab buttons; a step rail inside the console shows Prepare ESXi and Install Windows locked with reasons. Both light and dark themes are tokenised (LCD goes backlit in dark). Rendered with Playwright: no console errors, no horizontal scroll at 400 px, 82 KB.

Left open by the designer after revision (9)
  • Add equipment still shows placing mode (DL380 armed, with its preview) and the Selected edit panel at the same time. Hiding the edit panel while a card is armed would hide the edit fields at rest, and the page contract and functionality list need them visible. Cancel clears the placing mode instead.
  • The current step keeps its red marker and underline. The two lenses disagreed: novice wanted red reduced, craft wanted red kept for the current step. I treated it as 'act here', documented that in the colour rules, and added a separate graphite 'viewing' state.
  • The 10 alert rows (times, components, messages) are illustrative. The facts give only the count and that they were logged before the erase. The note says so, but the rows are still invented content: they are written to agree with the bay conflict (bays 3, 4 and 9 missing; bay 5 new).
  • 'Disks reported 6 · Proven 08:35' assumes the 08:35 inventory read also listed the drives, which is the craft reviewer's suggestion. The facts only say the server was reached at 08:35, and the drive list comes from the 24/09 erase record.
  • The Redfish request bodies in the dialogs are from memory of the HPE iLO 5 SmartStorageConfig API, not checked against app/backend/app/providers/ilo_redfish.py: PATCH /redfish/v1/Systems/1/smartstorageconfig/settings/ with PhysicalDriveErase / SanitizeRestrictedOverwrite, and ClearConfigurationMetadata. They should be confirmed before the design is treated as exact.
  • Drag-and-drop and the remove zone are visual only. The tap flow (card, then preview, then Move/Cancel) works in JS, but actual drag events, placing units and removal are not wired.
  • The Connect equipment frame is about 1750 px tall because the full 10-row alert table sits on it. Plan new RAID is above the fold, but 'Continue to Check firmware' is at the bottom. I did not collapse the alert table, because the blocker asked for the alerts to be listed.
  • 'Trust this certificate…' does not show a fingerprint value, because no fingerprint exists in the facts and inventing one would add a fact.
  • Only the light theme was re-screenshotted after the changes. Dark tokens were extended (new --signal-top/bot/text, --faint, --scrim) but not visually re-checked.

Left open by the designer after revision (6)
  • The page still renders in quirks mode (document.compatMode is 'BackCompat'). The page contract requires the file to start with <title> and forbids doctype, html, head and body tags, so <!doctype html> and <html lang> cannot be added. I added the charset and viewport meta tags, set lang from script, and added a table font-size guard to limit the quirks effects.
  • The 10 hardware alerts are listed as 10 rows, but component and severity are shown as blank ('only the count was kept'). The facts give only the count, and inventing alert details would break the rule about using only the given facts and never inferring.
  • In the elevation, the plan-occupied bays are drawn in graphite rather than filling the six reported disks in ink. The controller bay addresses (1I:1:1, 1I:1:2, 2I:1:5–8) cannot be mapped to front bay numbers without inference.
  • Suggested appears only on A-2 (the DL380 name and bottom slot). A-3 MTU 1500 stays a saved-plan value, because the facts say it is saved; only its gloss mentions that 1500 is the usual value.
  • Locked tabs A-6 and A-7 have no sheet. The brief allows them to be shown as locked steps with their reason rather than drawn. They are aria-disabled and show the reason in the tab.
  • At 4–5 U the A-2 drawing keeps its 600-unit viewBox width, so the rack sits left of centre where the callout would be. I left it that way so the drawing's scale does not jump as the stepper changes.

Designer's summary

Direction 6 renders Lab Builder as an operations console for professional operators: a topbar with kit controls and a Ctrl+K command palette, a persistent left status rail carrying the six build steps (5 and 6 locked with reasons) plus per-device telemetry LEDs, a central workspace, and a right-hand evidence drawer on every screen that shows the exact last read-only probe (request, HTTP status, latency, timestamp, returned fields, or the failure). The rack is a softly glowing schematic on a faint grid whose LEDs light green only from proof bound to that device today; all other values wear mono provenance chips (proven with timestamp, saved plan, suggested, blank, or a hollow LED for never-answered devices). Layered dark neutrals (never pure black) with one electric blue accent reserved for primary actions, focus glow, selection and the drop preview; semantic colours carry state only; a separately designed light palette. Six screens: My Rack (elevation + list, readiness tiles, provenance table, open technical-details disclosure, report an issue), Add equipment (4–60 U stepper, seven-card hardware tray with a DL380 mid-drag, ghost preview naming U5–U6 and stating nothing moves, remove zone, full edit panel with 10-bay grid, move/remove, save/copy/load/continue), Network settings (subnet/gateway/VLAN/MTU, blocked storage options with reasons, DNS/NTP/SNMP rows), Connect + Drives & RAID (connection form with TLS toggle, verified erase banner with three stage chips, six-disk table, boot-mirror/storage/spare readouts, four guarded secondary actions, stale-alerts banner, and a two-step write preview showing the exact Redfish POST with a blocked-with-reason confirm), Check firmware (SPP package row, order-of-work strip, per-device rows with Check against SPP / Saved readings / Review upgrades disabled with reason, switch not supported yet, Continue blocked with reason), and First contact failed (Certificate not trusted drawn in full with what was tried, what to check in order, editable saved details, all seven failure modes listed, no invented model or bays). A Designer's note lists audience, metaphor, palette, type pairing and a functionality-to-screen map. Rendered in both themes with Playwright: no console errors, no horizontal scroll at 400px, file is 88 KB.

Left open by the designer after revision (7)
  • The 10 alert rows (times, levels, parts, messages) are illustrative. The brief's facts only give the count, and the reviewers required rows. I avoided any drive-failure message so the rows never change which drives can be used for RAID, and labelled them 'recorded message · current state unknown'.
  • Facts reconciliation: the brief's 'bays 1–4 and 6–9 occupied' is now treated as the operator's saved bay plan, and the proven read supplies 8 present / 6 identified at 1I:1:1, 1I:1:2 and 2I:1:5–8. The UI shows the disagreement and suggests adopting the read, rather than changing the given facts.
  • The facts say 'Next action: plan new RAID', but I made 'Check alerts now' the Connect primary, as the reviewers asked and as the order of work requires. Plan new RAID stays one click away as the secondary.
  • Glossary terms use title-attribute tooltips, which appear on hover. The key terms also have visible helper text, but not every term does, to avoid noise on this pro-cohort screen.
  • The dark theme is set by the page script, because the page contract forbids an <html> tag. Before the script runs, the page follows the OS theme for a moment.
  • The palette swatches in the Designer's note keep inline hex backgrounds. They illustrate the palette rather than style a component, the same as the original.
  • The boot-pair value '1I:1:1 + 1I:1:2' still wraps to two lines in the narrow tile on the Connect screen. I left it after one fix pass, as the process allows only one.
